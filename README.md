# ParkingScore

Python-сервис периодически сканирует FTP, находит пары фотографии и XML с
одинаковым базовым именем, оценивает целевой автомобиль через модель
`cifra48/agent` и создаёт рядом с фотографией одноимённый TXT-файл.

Пример для `photo-id.jpg`:

```text
probability=82
best=false
```

В корне FTP ежедневно создаётся журнал с именем `dd-mm-yyyy.log`. Файл имеет
UTF-8-кодировку, строку заголовка и шесть столбцов, разделённых табуляцией:

```text
дата оценки	время оценки	папка на ftp сервере	имя факта	оценка	лучший
19-08-2026	14:32:10	/DozorMA687	photo-id	82	false
```

Дата и время рассчитываются в `ASSESSMENT_LOG_TIMEZONE` (по умолчанию
`Europe/Moscow`). Файл текущего дня создаётся даже при отсутствии новых оценок
и в этом случае содержит только заголовок. В журнал попадают только оценки,
фактически выполненные после включения этой функции; старые оценки из SQLite не
переносятся задним числом. Журнал атомарно обновляется только при изменении
содержимого, поэтому перезапуски не создают дубликаты. После закрытия серии
значение `лучший` обновляется с `false` на `true`. Повторная оценка после
изменения критериев записывается отдельной строкой с фактическими датой и
временем новой оценки.

После закрытия серии ровно один файл — снимок с максимальной вероятностью —
получает `best=true`. При равной вероятности выбирается более ранний снимок,
затем имя файла в лексикографическом порядке.

## Логика обработки

1. FTP сканируется рекурсивно от `FTP_ROOT_DIR`.
2. Фотография и XML считаются парой, если лежат в одной папке и имеют одинаковое
   имя без расширения.
3. В обработку допускаются только факты, у которых в XML поле
   `Coordinates/Pdop` имеет числовое значение `1.1`. Отсутствующее, пустое,
   нечисловое или другое значение исключает пару из очереди, серий и выбора
   `best`. Результат фильтра сохраняется в SQLite и проверяется повторно при
   изменении сигнатуры фото или XML.
4. Пара обрабатывается только после `FTP_STABLE_POLLS` сканирований без изменения
   размера и времени модификации. Это защищает от чтения незагруженного файла.
5. Из XML используются:
   - `CaptureInfo/Number` — ГРЗ;
   - `CaptureInfo/Date` — время снимка;
   - `Address` — место (при отсутствии используются координаты);
   - `CameraSerialNumber` — камера;
   - если `CameraSerialNumber` отсутствует, камера определяется по
     `SerialNumber + PositionCamera`, затем по имени FTP-каталога;
   - `ImagesInfo/Position` — координаты номера целевого автомобиля.
6. Серия строится по `ГРЗ + место + камера`. Следующий снимок входит в серию,
   если интервал от предыдущего не больше `SERIES_WINDOW_MINUTES`.
7. Пока после последнего обнаруженного снимка не прошло окно серии, все её
   результаты имеют `best=false`. После закрытия серии выбирается максимум.
8. Внутри очереди снимки оцениваются от старых к новым по
   `CaptureInfo/Date`. Новые неоценённые файлы по-прежнему имеют приоритет над
   фоновой переоценкой ранее обработанных снимков.

Перед отправкой в AI создаётся локальная копия изображения с пурпурной рамкой
вокруг номера целевой машины. Исходное фото на FTP не меняется. Фото передаётся
API как base64 data URL; ответ запрашивается как строгий JSON и валидируется.

AI-запросы выполняются параллельно пулом из `AI_WORKER_THREADS` потоков. Задания
передаются в пул от старых снимков к новым, но из-за разного времени ответа AI
могут завершаться в другом порядке. Запись SQLite, пересчёт `best` и публикация
TXT выполняются последовательно, без конкурентного изменения состояния.

Начало запросов распределяется общим ограничителем
`AI_REQUESTS_PER_MINUTE`, действующим сразу на все потоки. При `429` весь пул
выдерживает общую паузу с учётом `Retry-After`; остальные временные ошибки
повторяются с экспоненциальной задержкой и случайным разбросом. Ответ AI может
содержать как строку, так и массив текстовых частей. Некорректный `200 OK`,
`429` или сетевой таймаут откладывают снимок, но не переводят его в окончательный
`failed` после достижения `MAX_PROCESSING_ATTEMPTS`.

Состояние, контрольные суммы критериев, ошибки и опубликованные значения хранятся
в SQLite. После перезапуска обработка продолжается без повторной отправки уже
актуальных снимков.

Раз в `PROGRESS_REPORT_INTERVAL_SECONDS` сервис записывает в таблицу
`progress_snapshots` снимок очереди и выводит в журнал строку вида:

```text
Progress report ftp_pairs=12500 stable_pairs=12498 assessed=8300 awaiting=4200 discovered=12490 failed=3 criteria=ab12cd34ef56
```

`ftp_pairs` — число стабильных пар `фото+xml`, прошедших фильтр `Pdop=1.1`,
`stable_pairs` — все стабильные пары до фильтра, `assessed` — число актуальных
оценок для текущей версии критериев, `awaiting` — разница между `ftp_pairs` и
`assessed`. Подсчёт выполняется на уже полученном при штатном сканировании списке
и не создаёт дополнительного обхода сервера. После смены критериев старые оценки
сразу перестают входить в `assessed`, а новый снимок прогресса записывается без
ожидания очередного интервала.

Если меняется `criteria.txt`, старые результаты помечаются устаревшими. Сначала
всегда обрабатываются новые снимки. Старые серии переоцениваются в фоне только
при пустой очереди новых; обновлённая серия публикуется после полной переоценки.

`criteria.txt` хранится на хосте рядом с `compose.yaml` и подключается в контейнер
в режиме read-only. Файл не включается в Docker-образ. Сервис перечитывает его в
начале каждого цикла, поэтому после изменения критериев контейнер не нужно
пересобирать или перезапускать.

Формат — один критерий на строку. Пустые строки и комментарии с `#`
игнорируются; маркеры и нумерация необязательны:

```text
# Пример критериев
1. автомобиль находится всеми колесами вне асфальта
2. на фото отчетливо видно бордюр
- вокруг автомобиля есть трава или деревья или кусты
```

## Запуск в Docker

```bash
cp .env.example .env
```

Заполните в `.env` значения `FTP_HOST`, `FTP_USER`, `FTP_PASSWORD` и
`AI_API_KEY`. Затем:

```bash
docker compose up -d --build
docker compose logs -f parking-score
```

Секреты из `.env` не попадают в образ и исключены из Git. SQLite и кеш хранятся
в Docker volume `parking-score-data`.

Однократный цикл для диагностики:

```bash
docker compose run --rm parking-score python -m parking_score once
```

## Локальный запуск

Требуется Python 3.11 или новее.

```bash
python -m venv .venv
. .venv/bin/activate
pip install -e '.[test]'
cp .env.example .env
python -m parking_score once
pytest
ruff check parking_score tests
```

## Важные параметры

| Переменная | По умолчанию | Назначение |
|---|---:|---|
| `POLL_INTERVAL_SECONDS` | `60` | Период сканирования FTP |
| `SERIES_WINDOW_MINUTES` | `15` | Окно объединения и ожидания закрытия серии |
| `FTP_STABLE_POLLS` | `2` | Число стабильных сканирований пары |
| `MAX_NEW_JOBS_PER_CYCLE` | `20` | Максимум новых AI-запросов за цикл |
| `MAX_REPROCESS_JOBS_PER_CYCLE` | `1` | Фоновая переоценка за цикл |
| `AI_WORKER_THREADS` | `4` | Количество одновременных AI-запросов |
| `AI_REQUESTS_PER_MINUTE` | `6` | Общий лимит начала AI-запросов; `0` отключает |
| `AI_RETRY_BASE_SECONDS` | `10` | Начальная пауза внутреннего повтора AI |
| `AI_RETRY_MAX_SECONDS` | `120` | Максимальная пауза внутреннего повтора AI |
| `AI_RETRY_JITTER_SECONDS` | `3` | Случайный разброс паузы между потоками |
| `PROGRESS_REPORT_INTERVAL_SECONDS` | `3600` | Период записи и вывода прогресса |
| `ASSESSMENT_LOG_TIMEZONE` | `Europe/Moscow` | Часовой пояс ежедневных FTP-журналов |
| `AI_IMAGE_MAX_BYTES` | `5000000` | Лимит подготовленного JPEG до base64 |

Сервис не удаляет и не перемещает исходные XML или изображения. При обновлении
результата он заменяет только созданный одноимённый `.txt` через временный файл и
FTP `RNFR/RNTO`.
